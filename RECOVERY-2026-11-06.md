## Cause and safety constraints

`server-02` (Intel N100) hosts Talos VM `101`, Kubernetes node
`controlplane-worker-2` (`192.168.1.201`). Its fan appeared seized. CPU package
temperature reached 95 C, all four physical cores ran near 500 MHz under load,
and thermal throttle counters were very high. Later temperature was 70 C and
CPU use improved after physical cooling changes, but fan repair is still needed.
`controlplane-worker-1` is `192.168.1.200` on `server-01`.

- Do not rely on a seized fan or disable thermal protection.
- There are TWO etcd members: powering off cp-2 loses quorum even if all volumes
  have cp-1 replicas. Storage evacuation alone does NOT enable single-node operation.
- Do not reset/bootstrap etcd, remove members, force-detach, manually salvage,
  or delete source replicas as a shortcut.
- All infrastructure commands below run in this repository's Nix environment.
- Live overrides can be overwritten by ArgoCD or Terraform. No Git commits or
  pushes were made by the assistant. For persistent GitOps changes, review,
  commit and push yourself; do not blindly sync during recovery.

## Why cp-2 is uncordoned but tainted

Cordon initially seemed appropriate, but Longhorn v1.13 explicitly refuses to
recreate an instance-manager pod when the Kubernetes node is unschedulable.
This left cp-2 source replicas unavailable. The assistant added the custom
NoSchedule taint BEFORE uncordoning cp-2; its instance manager then became Ready.

Kubernetes tainting alone did NOT stop Longhorn replica placement onto cp-2.
SearxNG completed an unwanted rebuild there and Forgejo database began another.
The separate Longhorn `spec.allowScheduling: false` override now prevents NEW
replica placement there without evicting source replicas.
